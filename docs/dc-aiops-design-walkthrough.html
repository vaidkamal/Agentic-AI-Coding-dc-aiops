2. The design decisions

Each entry: what I chose, what I rejected, and why. Full records with consequences and revisit-when conditions are in docs/design-decisions.md.

Detection methodRolling z-score, window 20, plus absolute ceilings

Each metric is compared to its own last 20 samples; three sigma above baseline flags an anomaly. Ceilings (27 °C per ASHRAE A1, 92 % CPU) catch slow drifts that would poison the baseline.

Rejected: isolation forest (needs training data and a backend), EWMA control charts (harder to explain). A z-score produces a sentence the operator can read.

Correlate before alarmingZone pass first; per-rack suppressed

Three or more racks rising together in a zone open one CRAC incident; per-rack thermal detectors are suppressed while it is open. The CRAC is the only shared dependency inside a zone.

Rejected: one alarm per rack with a grouping view: that is the problem the goal spec describes.

Human approves, agent executesRunbooks are approval-gated; nothing is actuated

startRunbook is reachable only from the Approve button; runbook steps page people and tools. Blast radius (Weekend 1) set the oversight level, not the agency level.

Rejected: auto-remediate above a confidence threshold. Revisit after 100 observed approvals with zero reversals, with a dry-run mode first.

Explainable incidentsCause, evidence and a confidence number on every incident

rca, summary and conf are part of the contract. Confidence is a rule constant (0.91 zone-thermal, 0.84 rack-CPU, 0.88 PSU, 0.62 single hot rack), and the UI and ADR-04 say so.

Detection in the browserThe backend feeds, authenticates and persists

24 racks at 0.5 Hz is trivial for a browser; the published demo runs with no backend; the reviewer reads one file. Revisit at more than one hall.

Rejected: stream processor; Prometheus alert rules only (cannot correlate across a zone).

One telemetry contractAdapters conform; the console never adapts

Snapshot is fixed in the API contract. The Prometheus adapter's PromQL is overridable per site because exporter metric names differ everywhere. A malformed snapshot is dropped and logged, never broadcast.

Feed loss degrades, announcedSimulator fallback with a toast and /healthz

Simulated data must never masquerade as real, so the fallback is always announced and reconnects every 5 s.

The AI feature is one model callStructured output, no tools, no loop, no runtime agent

Weekend 6 flowchart: rules cannot parse free text (Hinglish, corrections) → test a model. Does it need evidence beyond the input? No: the note, the zone/CRAC map and the runbook catalogue suffice. So: POST /ai/triage, one AsyncAnthropic call with a declared response model, post-validation in code, 20 s timeout, 1,024 tokens, no retries.

Rejected: an agent with a telemetry-lookup tool (no evidence it is needed yet; revisit if ≥ 20 % of real notes need live data), rule-based parser, fine-tuning.

The model proposes; the application savesNo write path from the AI module

The triage response carries no incident id and no permission to write. The console tracks confirmation; POST /incidents is the only write and is called with the exact reviewed fields. A test asserts that backend/ai/ references nothing that writes; adding such a reference turns the build red (verified by mutation).

Limits in code, not in token capsBudget reserve/settle, rate limit, 429 with a reason

Token caps bound one call, not monthly spend. Reserve before, settle after, against AI_MONTHLY_BUDGET_USD; 10 requests/min/user, documented as process-local.

Observability through OpenTelemetry to PhoenixOff by default; the gap is visible

Five named spans per triage call plus a separate incident.save trace linked by request id; API key and bearer redacted; /healthz reports tracing: off when no collector is set.

Golden set and deterministic checks first; judge secondThe expert approves the rule; the agent implements the check

Eight cases chosen by dimension (zone vs rack, typo ids, vague, Hinglish correction, pasted log, below threshold, injection). Mocked checks run in CI and never pay for a model call; live runs ask for budget approval; the judge rubric covers only the two semantic criteria and must be calibrated against expert labels before it is trusted.

Deployment with recovery proofECS Fargate + RDS via Terraform; backup before destroy

destroy.sh takes a manual RDS snapshot and aborts the destroy if the snapshot fails. restore.sh rebuilds from the snapshot, triggers the deploy workflow, and greps the API for a known INC-nnn. Cloudflare Quick Tunnel is the alternative for a temporary demo of the local app.

Rejected: Render/Fly.io (less control over the restore exercise), Kubernetes (more than one hall needs).

3. Trade-offs I would defend

Simplicity over sophistication in the models

Every analytic can be explained in one sentence and recomputed by hand. In operations, a model nobody trusts is a model nobody uses. Heavier methods can replace them behind the same incident contract once there is history to train on.

Minimal viable agent for the AI feature

A single call with structured output solves the task the spec describes. Adding a tool or a loop without evaluation evidence would be complexity without a reason, and it would widen the authority surface I have deliberately kept at zero.

In-memory incident store in v1

The ticketing system is the record in v1. This is also the one place the specs and the code disagree today (backend-spec requires PostgreSQL); it is recorded as blocking Phase 7's restore proof, not hidden. T16 is the next task.

5. Interview preparation

I wrote 25 questions that can only be answered by understanding the code (docs/interview-questions.md) and answered them without opening the repo. The ones I expect most:

Trace one operator note to a saved incident. Which call writes?

POST /api/v1/ai/triage returns a draft, missing fields and a reply; it writes nothing. The operator edits and confirms; the console calls POST /api/v1/incidents with the exact reviewed fields and two headers linking the save to the triage trace. The model is not called at that step.

Why not an agent for triage?

The two flowcharts: rules cannot parse free text, so a model; the model does not need evidence beyond the input, so one call. An agent would add authority and cost without a measured benefit. The revisit condition is written down: if evaluation shows notes need live telemetry to classify, compare one bounded tool call against the baseline on the same cases.

What happens when the provider times out?

503 after 20 s, no SDK retry, the draft is preserved client-side, manual entry is offered, and nothing is ever replayed automatically. The same rule applies to a lost save response: the operator is told the incident may already exist and to check the Incidents tab.

Where is the authority boundary and which test guards it?

All writes require a bearer token; the model has no write path; runbooks do not actuate. The import-boundary test fails if backend/ai/ references the incident router. I verified that by adding the reference and watching it go red.

Give one example where the spec was fixed before the code.

The builder found that kind: "other" with clarification_fields: ["kind"] contradicted the contract's "union equals null fields" invariant. I amended the contract and the AI spec to say "not catalogued counts as unresolved" and only then accepted the code. Another: the contract said /api/v1 and the code served /api; the code moved, with a dated deprecated alias.

Why does CI run only the mocked evaluation?

Mocked checks protect logic and cost nothing; live evaluation tests behaviour with the real provider and costs money, so it runs on request with an explicit budget approval and before accepting a prompt or model change. A judge is used only for the two semantic criteria and only after calibration against expert labels.

What survives teardown?

The RDS snapshot, Terraform state and the database password, each retained separately. ECR is recreated empty so the image is re-published; CloudFront gets a new hostname so the console config is updated; tokens come from the IdP so nothing is regenerated. The proof is the same INC-nnn with its original opened timestamp after rebuild; today that proof is blocked by the in-memory store, and the plan says so.

What did the agent get wrong, and how did you catch it?

Three things. The first package shipped without spec files. The workspace was recycled between sessions and the code had to be recreated from the session record, which taught me to commit after every turn. And the builders reported eleven spec-versus-code questions rather than patching around them; each got a decision and the affected documents were updated before the code changed.
